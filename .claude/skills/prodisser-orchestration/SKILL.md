# Оркестрация доработки ProDisser

Навык описывает, как основной сеанс (оркестратор) ведёт выпуск силами
агентов. Что и как править на страницах — навык `prodisser-visual-style`;
решения владельца — `docs/DECISIONS.md`. Решение владельца сильнее этого
порядка.

## 1. Роли

| Роль | Кто | Модель | Что делает | Чего не делает |
|---|---|---|---|---|
| Оркестратор | основной сеанс, с которым говорит владелец | Fable 5.2 (распределение ролей владельца 20.11.2026; модель сеанса переключает владелец — `/model`) | ведёт цикл, задаёт вопросы владельцу, распределяет работу, сливает ветки, создаёт запрос, выкатывает по согласию, отчитывается | не правит страницы сам, если работу можно поручить; не сливает в `main` без согласия |
| `prodisser-architect` | агент | Fable 5.2 | план выпуска, сверка с журналом и законом, вопросы-квиз, приёмка диффов | не пишет код |
| `prodisser-analyst` | агент | Opus 5.5 | замер страниц против эталона, снимки «до», предложения | не меняет репозиторий |
| `prodisser-site-dev` | агент | Opus 5.5 | правки макетов, тесты, журнал, коммиты в своей копии | не пушит, не сливает |
| `prodisser-cabinet-dev` | агент | Opus 5.5 | правки кабинета, тесты на базе, пересъёмка артбордов | не пушит; одновременно — один |
| `prodisser-verifier` | агент | Opus 5.5 | полный прогон проверок ветки выпуска, просмотр глазами | не меняет код |

Определения агентов — `.claude/agents/*.md`. Если сеанс открыт не в этом
репозитории и агенты не подхватились как типы, оркестратор запускает
`general-purpose` с моделью из заголовка файла и начинает задание текстом
файла агента (без заголовка), затем — конкретика задачи (§4).

## 2. Цикл выпуска

Выпуск — субботний (Р-626); вне субботы — только аварийное или по прямому
указанию владельца.

| Шаг | Кто | Результат | Точка владельца |
|---|---|---|---|
| 0. Сверка | оркестратор | последний выкат и отчёт цепочки, открытые запросы, `accepted/*`, ветки впереди `main`, замечания с кнопки | — |
| 1. Разбор | аналитики параллельно, по странице на агента | `proposals/<страница>.md`, снимки «до» | — |
| 2. План и вопросы | архитектор | план выпуска, пакеты квиза | ответы на квиз |
| 3. Распределение | оркестратор | рабочие копии (`wt-new.sh`), диапазоны номеров решений, задания | — |
| 4. Разработка | разработчики параллельно, в фоне | коммиты в своих ветках | — |
| 5. Приёмка диффов | архитектор (или оркестратор) | «принять» / «вернуть» по каждой ветке | — |
| 6. Интеграция | оркестратор | ветки слиты в ветку выпуска (`wt-merge.py`) | — |
| 7. Проверка | проверяющий | таблица `release-check.sh`, вердикт | — |
| 8. Запрос | оркестратор | PR по шаблону, подписка на события, CI зелёный | — |
| 9. Выкат | оркестратор | слияние, «Выкат на боевой сервер», «Сайт отвечает снаружи», отчёт со ссылками | **согласие на выкат** |
| 10. Приёмка | оркестратор | запись приёмки на коммите только с документами поверх выкаченного `main`, ветка `accepted/<сайт|кабинет>-<дата>`, слияние записи в рабочую ветку `wt-merge.py` | **«принято»** |
| 11. Уборка | оркестратор | `wt-done.sh` по каждой копии | — |

Шаги 1—2 и 4—7 разных выпусков могут идти внахлёст: работа следующего
выпуска ведётся в локальных ветках от ветки текущего, а в ветку открытого
запроса не пушится ничего, кроме исправлений этого запроса.

## 3. Распределение

- **Одна страница — один разработчик**: конфликты макетов `design/*.dc.html`
  и порождённых `.tsx` не разбираются вручную. Сквозная правка всех страниц
  (кнопка, метка) — одному разработчику до или после постраничных правок.
- **Кабинет — один разработчик за раз**: пересъёмка артбордов и прототипа
  (отпечаток Р-214) у двух веток гарантированно расходится.
- **Номера решений** — диапазон на каждого исполнителя заранее, от
  `journal-append.py --next` на свежем `main` с учётом открытых запросов и
  локальных веток. Записи пишутся только `journal-append.py`.
- **Рабочая копия**: `bash .claude/skills/prodisser-orchestration/scripts/wt-new.sh <имя> [основа]` —
  worktree `/home/user/wt-<имя>`, ветка `<имя>`, `node_modules` жёсткими
  ссылками, `prisma generate`, блок портов (3410…3499 по десять) и префикс
  баз. Порты 3400—3409 — оркестратора (3401 — сервер состояния `main` для
  разборов, 3402 — сборка ветки выпуска).
- **Сервер состояния `main` для разборов**: `wt-new.sh main-view origin/main`,
  сборка `npm run build` с `DATABASE_URL=postgresql://ci:ci@127.0.0.1:5432/ci`
  и `NEXT_PUBLIC_SITE_URL=https://prodisser.ru`, запуск `PORT=3401 HOSTNAME=127.0.0.1 … node .next/standalone/server.js`.

## 4. Задание исполнителю

Агент знает только то, что в задании. Обязательно:
1. Цель и решения владельца дословно (тексты — точно, с датой ответа).
2. Рабочая копия, ветка, основа; блок портов; префикс баз; номера решений.
3. Что не трогать (страницы других исполнителей, первый экран, формы).
4. Исходные материалы: пути к разборам, снимкам, записям Р-NN.
5. Проверки (`release-check.sh` с ключами) и каталог для снимков «до/после».
6. Подпись коммитов — две строки сеанса-оркестратора (Co-Authored-By с
   моделью исполнителя и Claude-Session с адресом сеанса).
7. Что вернуть: коммиты, проверки числами, снимки, сомнения.

Агенты запускаются в фоне; оркестратор не повторяет их работу и не
предсказывает результат до уведомления.

## 5. Интеграция

На ветке выпуска, с чистым деревом:

    python3 .claude/skills/prodisser-orchestration/scripts/wt-merge.py <ветка>

Скрипт сливает без коммита, журнал и сводку собирает «наши, затем их»
(записи ветки — `journal-append.py`, по номеру; строки «Приёмки» — после
последней нашей), сверяет, что прежние строки целы, заголовки не
повторяются и текст дописанных записей совпадает с веткой. Конфликт вне
журнала — код выхода 2: разобрать вручную; для макетов после разбора —
`sync-check.sh`, порождённые `.tsx` не правятся руками. Затем
`release-check.sh` и коммит слияния с подписью.

## 6. Вопросы владельцу

Только где нужен выбор (класс Р и К); класс А делается без вопроса и
перечисляется в отчёте. Квиз: до 4 вопросов в пакете, 2—4 варианта, первый —
рекомендуемый «(рекомендую)», у варианта — последствие и точный новый текст.
Вопрос понятен без переписки выше (окно квиза закрывает текст). Ответ «без
предпочтения» — делается рекомендуемое и показывается снимками до выката.

## 7. Уроки, которые уже стоили времени

- `pkill -f "standalone/server.js"` не находит серверы: процесс называется
  `next-server`. Останавливать по PID, найденному по рабочему каталогу
  (`readlink /proc/<pid>/cwd`); `wt-done.sh` делает это сам.
- В worktree `.git` — файл, а не каталог: временные файлы — в `tempfile`.
- `NODE_PATH` не действует на `import` в `.mjs`: Playwright —
  `import { chromium } from '/opt/node22/lib/node_modules/playwright/index.mjs'`.
- Журнал — 42 тысячи строк: сверка строк — через множества, не через
  поиск в списке в цикле.
- Одновременно не больше трёх-четырёх сборок в контейнере: иначе проверки
  растягиваются вдвое.
- Слово «вычитка» стояло в свёрнутом перечне, «гарантии» — в `aria-label`:
  тексты проверяются по всему макету (`site-forbidden-words`), не только
  видимые.
- Запись приёмки делается на коммите с одними документами поверх
  выкаченного `main` (ветка `accepted/*` указывает на код выката), потом
  сливается в рабочую ветку.

## 8. Скрипты

| Скрипт | Назначение |
|---|---|
| `scripts/wt-new.sh <имя> [основа]` | рабочая копия исполнителя, порты, базы |
| `scripts/wt-done.sh <имя> [--force]` | остановить её серверы по PID, удалить её базы, убрать копию; ветка удаляется, если влита |
| `scripts/wt-merge.py <ветка>` | слияние с журналом «наши, затем их» и сверкой |
| `scripts/release-check.sh [копия] [--site пути] [--port N]` | перенос макетов, типы, тесты, тесты на свежей базе, сборки, `landing-audit` с axe и `ui-checks` |
