# Размещение сайта

Инженерная сторона: команды, настройки, проверки. Пошаговая инструкция для
владельца — «что купить и куда нажать» — в `docs/HOSTING.md`.


Что нужно сделать, чтобы сайт открылся по адресу и начал принимать заявки.
Порядок важен: пункты 1–3 выполняются до публикации, а не после.

## 0. Что уже готово в репозитории

| Файл | Назначение |
|---|---|
| `app/Dockerfile` | образ приложения, многоэтапная сборка |
| `deploy/docker-compose.yml` | приложение, база и разовый накат миграций |
| `deploy/.env.deploy.example` | образец окружения — скопировать в `deploy/.env` |
| `deploy/nginx.conf` | обратный прокси, перенаправления, сертификат |
| `deploy/nginx-bootstrap.conf` | временный узел на время выпуска первого сертификата |
| `deploy/backup.sh` | ежедневная копия базы, хранение 30 дней |
| `deploy/restore-check.sh` | проверка, что копия восстанавливается: временная база, сверка, удаление |
| `deploy/outbox.sh` | рассылка уведомлений кабинета по расписанию |
| `deploy/update.sh` | обновление сайта: копия базы, миграции, сборка, проверка здоровья, откат |
| `deploy/retention.sh` | еженедельное удаление заявок с истёкшим сроком хранения |
| `app/src/app/api/health/route.ts` | проверка живости: отвечает 503, если база недоступна |

Образ собирается в четыре слоя: зависимости, сборка, **накат миграций** и
рабочий. Слой миграций отдельный намеренно — в рабочем образе Next оставляет
только модули, которые требует `server.js`, командной строки prisma там нет.

## 1. Площадка

**Обязательные условия, не подлежащие обсуждению:**

1. Провайдер состоит в [реестре хостинг-провайдеров Роскомнадзора](https://rkn.gov.ru/activity/connection/register/p1578/).
   Требование действует с декабря 2023 года.
2. Сервер базы физически находится в России — ч. 5 ст. 18 152-ФЗ: запись,
   систематизация, накопление и хранение персональных данных граждан РФ
   выполняются с использованием баз на территории страны. Резервные копии
   тоже остаются в России: копия — это та же обработка.

**Рекомендация: Timeweb Cloud, 2 vCPU / 2 ГБ / 40+ ГБ NVMe и файл подкачки
на 2 ГБ. Переход на 4 ГБ — когда появятся кабинет и админ-панель.**

Размер выбран по замерам, а не на глаз (замерено 23.08.2026 на этом проекте):

| Что | Сколько |
|---|---|
| приложение в работе (`node server.js`) | 49 МБ |
| PostgreSQL в работе | 84 МБ |
| пик сборки образа (`npm run build`) | ~1000 МБ |
| готовая сборка на диске (standalone + static + public) | 75 МБ |
| `node_modules` на время сборки | 828 МБ |

В покое приложение с базой занимают около 130 МБ; вместе с системой и Docker
это порядка 500 МБ. Единственный всплеск — сборка образа, и его закрывает
файл подкачки. Поэтому 2 ГБ достаточно, а 4 ГБ нужны, когда на той же машине
появятся кабинет и админ-панель.

Файл подкачки создаётся один раз:

```bash
fallocate -l 2G /swapfile && chmod 600 /swapfile
mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
```

Диск: 40 ГБ с запасом. Сама сборка занимает 75 МБ, но Docker держит слои
образа и кэш — раз в пару месяцев `docker system prune -f`.

Почему Timeweb: в реестре РКН, почасовая тарификация (можно поднять, проверить
и погасить), понятная панель, есть управляемый PostgreSQL на случай, если
базу захочется вынести отдельно. По состоянию на 2026 год конфигурация
2 vCPU / 2 ГБ обходится примерно в 700–900 ₽ в месяц, 4 ГБ — около 1500 ₽,
внешний адрес IPv4 оплачивается отдельно, порядка 180–200 ₽ в месяц
([обзор тарифов](https://hostinghub.ru/timeweb-cloud)).

Достойные равноценные варианты: **Selectel** (минимальный облачный сервер
около 940 ₽, инфраструктура крупнее, панель сложнее), **Beget** и **REG.RU**
(дешевле, удобны, если домен уже у них). Все четыре — в реестре РКН.

Отдельно: и Timeweb, и Selectel подняли цены в конце 2025 — начале 2026 года
на 8–20 %, так что цифры выше стоит перепроверить на дату покупки.

**Чего не делать.** Не размещать на зарубежной площадке — ни Vercel, ни
Netlify, ни зарубежный VPS. Дело не в доступности из России, а в том, что
персональные данные заявителей окажутся в базе за пределами страны.

## 2. Домен и почта

## 3. Уведомление Роскомнадзора

Подать **до открытия сайта**, а не после. Уведомление о намерении
осуществлять обработку персональных данных подаётся через портал
Роскомнадзора; сведения в нём — цель обработки, перечень данных, сроки
хранения, сведения о трансграничной передаче — должны совпадать с
опубликованной политикой. Сроки хранения в политике на момент написания
выбраны предположительно и требуют согласования с юристом (см.
`docs/DECISIONS.md`).

## 3а. Обязательное условие: приложение работает только за nginx

Контейнер слушает `127.0.0.1:3000` и снаружи недоступен. Это не только защита
портов: адрес заявителя приложение берёт из заголовка `X-Real-IP`, который
проставляет наш nginx из настоящего адреса соединения. Заголовок
`X-Forwarded-For` для этого не годится — его присылает сам клиент, и подделка
дала бы обход ограничения частоты и чужой адрес в журнале согласий
(см. `docs/DECISIONS.md`, Р-30).

Выставлять контейнер в интернет напрямую или ставить перед ним другой прокси
без `proxy_set_header X-Real-IP $remote_addr` нельзя.

Заголовки безопасности, включая политику содержимого, отдаёт само приложение;
`Strict-Transport-Security` добавляет nginx. Проверить после запуска:

```bash
curl -sI https://prodisser.ru | grep -iE 'content-security|strict-transport|x-frame|x-content'
```

## 4. Развёртывание

```bash
# на сервере
git clone <репозиторий> /opt/prodisser
cd /opt/prodisser

cp deploy/.env.deploy.example deploy/.env
nano deploy/.env          # адрес сайта, пароль базы, Telegram, почта

# первый запуск: сначала схема, потом приложение
docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
  --profile migrate run --rm migrate
docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
  up -d --build

curl -s http://127.0.0.1:3000/api/health      # ожидается {"ok":true,"db":true}
```

Публичный адрес обязателен на сборке, а не только при запуске: `canonical`,
Open Graph, `robots.txt` и карта сайта вычисляются из него. Если собрать образ
без него, карта сайта уйдёт с относительными адресами и станет недействительной.
`docker compose` передаёт значение в сборку сам, но при ручной сборке образа
нужен `--build-arg NEXT_PUBLIC_SITE_URL=https://prodisser.ru`.

Обратный прокси и сертификат:

```bash
apt install nginx certbot python3-certbot-nginx
cp deploy/nginx.conf /etc/nginx/sites-available/prodisser
ln -s /etc/nginx/sites-available/prodisser /etc/nginx/sites-enabled/
certbot --nginx -d prodisser.ru -d www.prodisser.ru
nginx -t && systemctl reload nginx
```

Наполнение справочников после первого развёртывания:

```bash
docker compose exec web npm run seed:reference
```

Заводятся шесть позиций типов сопровождения и таблица заливок книги заказов.
Скрипт идемпотентен и не затирает правки, внесённые руководителем через
кабинет. Первая учётная запись руководителя заводится вручную запросом к базе
либо `scripts/seed-cabinet.ts` на стенде: экран «Пользователи» доступен только
руководителю, и завести первого из кабинета не из кого.

Устройство закрытого раздела, роли и сроки хранения — `docs/CABINET.md`.

Резервные копии и срок хранения:

```bash
crontab -e
# 0 3 * * * /opt/prodisser/deploy/backup.sh >> /var/log/prodisser-backup.log 2>&1
# 30 3 * * 1 /opt/prodisser/deploy/retention.sh >> /var/log/prodisser-retention.log 2>&1
# 0 4 1 * * /opt/prodisser/deploy/restore-check.sh >> /var/log/prodisser-restore.log 2>&1
# * * * * * /opt/prodisser/deploy/outbox.sh >> /var/log/prodisser-outbox.log 2>&1
```

Третье расписание рассылает уведомления кабинета. Отдельного процесса-демона
для этого не заводится: при семи типах событий и нескольких десятках проектов
он был бы компонентом «на вырост». Маршрут закрыт общим секретом, а не
сессией — у расписания учётной записи нет, — и слушает только петлю: наружу
приложение и так не выставлено.

Вызов вынесен в скрипт, а не записан строкой с `curl` прямо в crontab: cron
не читает `deploy/.env`, и подстановка `$CABINET_CRON_SECRET` дала бы пустой
заголовок — расписание выглядело бы исправным, а рассылка молчала бы. Скрипт
читает секрет из файла сам и пишет строку в журнал, только когда что-то
отправлено или произошла ошибка: иначе там набиралось бы полторы тысячи строк
«ничего не делалось» в сутки.

Раз в минуту, а не раз в час, потому что уведомление о том, что этап ждёт
материалов, теряет смысл тем быстрее, чем дольше идёт. Пустой вызов стоит
одного запроса к базе.

Второе расписание с этого выпуска чистит не только заявки: вместе с ними
уходят погашенные ссылки входа старше 30 дней, истёкшие и отозванные сессии
старше 90 дней и записи попыток входа старше 90 дней. Это идентификаторы
пользователей без всякой цели обработки; журналы действий и доступа к файлам
не трогаются — у них своя задача и свой срок.

Второе расписание — не удобство, а исполнение обещанного. Политика обработки
персональных данных, п. 7.1, обязывает хранить данные заявителей не более
года с даты обращения, если договор не заключён. Обещание в опубликованном
тексте без исполнения в коде видно проверяющему в первой же выгрузке из базы.
Скрипт удаляет заявки старше двенадцати месяцев, не трогая записи со статусом
`CONTRACTED`: по ним договор заключён и действует п. 7.2. Сначала считает,
потом удаляет, и пишет число в журнал — молчаливое удаление персональных
данных нельзя проверить ни через день, ни через год.

Скрипт пишет дамп во временный файл, проверяет целостность архива и его размер
и только потом заменяет им дневную копию и удаляет просроченные. При отказе
`pg_dump` копия не создаётся, а скрипт завершается с ненулевым кодом — cron
пришлёт письмо. Без этой проверки в каталоге накапливались бы пустые архивы,
и это выяснилось бы при первой же попытке восстановления.

### Проверка восстановления

Копия, которая не восстанавливается, — не копия. Файл на диске выглядит
одинаково и когда дамп полон, и когда он снят с пустой базы или оборван на
середине; разница видна только при восстановлении. Проверка делается
скриптом:

```bash
/opt/prodisser/deploy/restore-check.sh                      # последняя копия
/opt/prodisser/deploy/restore-check.sh deploy/backups/prodisser_2026-09-16_0300.sql.gz
```

Скрипт разворачивает копию во временную базу рядом с боевой, сверяет состав
и удаляет временную базу — в том числе при падении проверки, иначе на сервере
копились бы базы с персональными данными. Рабочая база не затрагивается:
совпадение имён проверяется до начала работы и прекращает её.

Что подтверждается: копия распаковывается и накатывается без ошибок; в ней
есть таблица заявок и перечень применённых миграций; число заявок не меньше,
чем в копии ожидалось. Строка в журнале показывает числа, а не слово
«успешно»:

```
2026-09-16T03:05:11+00:00 копия восстановлена: prodisser_2026-09-16_0300.sql.gz,
таблиц 3, заявок 407 (в базе сейчас 409), миграций 2
```

Заявок в базе больше, чем в копии, — это норма: они прибывают между снятием
копии и проверкой. Обратное соотношение выводит предупреждение: либо дамп
оборван, либо записи удалялись.

Запускается вручную после первой ночной копии и раз в месяц по расписанию:

```
0 4 1 * * /opt/prodisser/deploy/restore-check.sh >> /var/log/prodisser-restore.log 2>&1
```

**Восстановление на другой машине** — отдельный случай: дамп снимается с
владельцами объектов, и на чужом сервере роль с тем же именем должна
существовать, иначе восстановление останавливается на `role "…" does not
exist`. Либо создать роль, либо снять дамп с `--no-owner`. Внутри своего
сервера, куда и восстанавливает скрипт, роль та же и вопрос не возникает.

## 5. Обновление сайта

**Обычно ничего делать не нужно: выкат идёт сам после слияния в `main`** —
раздел 5г. Вручную, если конвейер недоступен:

```bash
cd /opt/prodisser && git pull
docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
  --profile migrate run --rm migrate          # если менялась схема
docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
  up -d --build
```

Миграции наносятся отдельным разовым запуском намеренно: приложение не должно
менять схему само — иначе два экземпляра при перезапуске полезут в базу разом.

## 5а. Отзывы: выгрузка в таблицу

Отзывы приходят той же формой, что заявки, и лежат в той же таблице с
пометкой `form = 'review'`. Читать их в базе неудобно, поэтому есть выгрузка
в CSV — его открывает любая таблица, облачная или настольная.

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
  --profile tools run --rm tools scripts/export-reviews.mjs --stdout > reviews.csv
```

Запуск идёт не в рабочем контейнере, а отдельным разовым: в рабочий образ
не попадают ни исходники, ни каталог `scripts` — так задумано, и `exec web`
такую команду не выполнит. Профиль `tools` поднимает образ со всем нужным на
один запуск и гасит его (решение Р-132).

Локально, без контейнера: `cd app && npm run reviews:export` — файл ложится
в `deploy/exports/reviews.csv`.

Столбцы: дата, страница, «кто», текст отзыва, «можно публиковать», состояние,
заметки, идентификатор. Состояние и заметки берутся из тех же полей заявки,
поэтому таблицу можно вести как реестр: что опубликовано, что отклонено, что
ждёт согласования.

**Столбец «можно публиковать» — первый, по которому сортируют реестр.** Он
показывает, отметил ли автор в форме разрешение на публикацию (решение
Р-114). Отзыв без разрешения опубликовать нельзя: форма не собирает ни имени,
ни контакта, поэтому спросить автора задним числом негде. Такой отзыв
остаётся внутренним сигналом «нам написали».

**Личных данных в файле нет по устройству формы.** Она спрашивает роль и
текст; контакт не собирается вовсе, и даже если значение придёт (прислал
робот), обработчик его не сохранит — решение Р-110. Поэтому файл можно
класть на облачный диск и вести там без оглядки на 152-ФЗ.

Порядок, если реестр ведётся на диске: выгрузить файл после каждого
поступления либо раз в неделю по расписанию рядом с `backup.sh`, загрузить в
папку на диске, открыть таблицей. Автоматической отправки в облако из
приложения намеренно нет: она означала бы ключ доступа к чужому сервису на
боевом сервере, зависимость от его доступности и данные, уходящие за пределы
контура без отдельного решения.

## 5б. Заявки: выгрузка в таблицу

**Временная мера, пока не подключены почта и Telegram.** Сейчас заявка
сохраняется в базу и больше нигде не видна. Чтобы не читать её запросом на
SQL, есть такая же выгрузка в CSV:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
  --profile tools run --rm tools scripts/export-leads.mjs --stdout > leads.csv
```

Локально, без контейнера: `cd app && npm run leads:export` — файл ложится в
`deploy/exports/leads.csv`.

Двадцать столбцов: дата, страница, форма, имя, контакт и его вид,
организация, тема, специальность, что нужно, срок, направление, сообщение,
согласие и его редакция, акцепт оферты, согласие на рассылку, состояние,
заметки, идентификатор. Журнал согласий выгружается целиком: именно он
предъявляется проверяющему. Отзывы в эту выгрузку не попадают — у них своя
(раздел 5а).

**В файле персональные данные, и он не покидает контур.** Это главное
отличие от выгрузки отзывов: там личных данных нет по устройству формы, и
файл разрешено вести на облачном диске. Здесь в файле имя, контакт,
организация и текст обращения. Загрузка его на внешний сервис — передача за
границу, которой Политика не допускает, и обработка вне базы на территории
России вопреки ч. 5 ст. 18 152-ФЗ. Файл хранится на сервере или на машине
оператора и удаляется, как только перестал быть нужен; каталог
`deploy/exports/` в репозиторий не попадает (`.gitignore`).

## 5в. Первый выкат кабинета

Личный кабинет собран и лежит в `main`, на сервере его ещё нет: последний
выкат был до того, как контур влили. Обновление с кабинетом отличается от
обычного тремя вещами, и без них раздел ответит ошибкой.

**0. До настройки раздел закрыт сам.** Слияние в `main` обновляет сервер
автоматически (раздел 5г), и кабинет уезжает туда вместе с сайтом. Пока не
заданы `SESSION_SECRET`, `CABINET_STORAGE_DIR` и `DATABASE_URL`, раздел
`/cabinet` отвечает страницей «Раздел готовится» и к базе не обращается —
ошибки сервера на живом домене не будет (решение Р-153). Открытие кабинета
поэтому остаётся отдельным действием: задать настройки ниже.

**1. Секреты.** Кабинет не поднимается без `SESSION_SECRET` — им
подписываются свёртки одноразовых ссылок и сессий. Развёртывание без него
прекращается с понятным текстом, а не поднимает сайт с неработающим
разделом. Значения получаются на сервере и в переписку не попадают:

```bash
cd /opt/prodisser
printf 'SESSION_SECRET=%s\n' "$(openssl rand -base64 48)" >> deploy/.env
printf 'CABINET_CRON_SECRET=%s\n' "$(openssl rand -base64 32)" >> deploy/.env
```

Смена `SESSION_SECRET` разом обесценивает все выданные ссылки и открытые
сессии — это и есть способ закрыть доступ всем сразу.

Там же задаётся каталог материалов — том, который переживает пересборку
образа:

```bash
printf 'CABINET_STORAGE_DIR=%s\n' /var/lib/prodisser/materials >> deploy/.env
```

**2. Миграции.** Контур добавляет таблицы, поэтому запуск с профилем
`migrate` обязателен, а не «если менялась схема»:

```bash
git pull
docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
  --profile migrate run --rm migrate
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --build
```

**3. Учётная запись руководителя.** В боевой базе кабинета нет ни одной
учётной записи: наполнение стенда работает только с адресами `@example.org`
и до боевой базы не допускается. Первая запись заводится на сервере:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
  --profile tools run --rm tools scripts/grant-role.ts info@prodisser.ru HEAD "Фамилия Имя Отчество"
```

Скрипт печатает ссылку входа — она действует час и срабатывает один раз.
Пока почта не подключена, это единственный способ войти: письма отправлять
некуда. Повторный запуск не плодит записи, а обновляет роль и имя и выдаёт
новую ссылку.

Учётные записи клиентов заводятся сами — при одобрении заявки.

**4. Расписание рассылки.** Уведомления кабинета разбирает `outbox.sh`,
который cron запускает раз в минуту (раздел 4). Без строки в crontab
уведомления копятся в очереди и не уходят:

```
* * * * * /opt/prodisser/deploy/outbox.sh >> /var/log/prodisser-outbox.log 2>&1
```

Секрет должен состоять из знаков ASCII — `openssl rand -base64` даёт именно
такие. Кириллица в общем секрете не годится: заголовки HTTP переносят её
искажённой, и маршрут отвечает «не найдено» при верном на вид значении.

После выката: `https://prodisser.ru/cabinet` открывает вход по ссылке;
`/cabinet/manage` показывает заявки с сайта в очереди рассмотрения;
`/cabinet/manage/registry` доступен только менеджеру и руководителю.

**Материалы работ.** Файлы кабинета хранятся не в базе, а в каталоге
`deploy/storage` на хосте — том контейнера. Каталог внутри образа не годится:
при пересборке содержимое контейнера теряется целиком. Ночная копия
архивирует этот каталог рядом с дампом (`storage_ГГГГ-ММ-ДД_ЧЧММ.tar.gz`) и
удаляет архивы по тому же сроку в тридцать дней: восстановление одной базы
дало бы кабинет, где ссылки на версии есть, а файлов нет.

## 5г. Автоматический выкат

Решение Р-151. Обновление сайта делается само: слияние в `main` → зелёная проверка → сервер
забирает код, снимает копию базы, накатывает миграции, пересобирает образ,
проверяет здоровье. Терминал для обновления больше не нужен.

Вся работа — в `deploy/update.sh` на сервере; конвейер только подключается по
ssh и запускает его. Поэтому то же обновление всегда можно повторить руками:

```bash
/opt/prodisser/deploy/update.sh
```

**Откат.** Если приложение не ответило за минуту, возвращается прежний образ
и прежний коммит, и выкат завершается с ошибкой — сайт не остаётся лежать.
Возвращается код, **но не схема базы**: миграции необратимы. Отсюда правило
для миграций — они пишутся так, чтобы прежняя версия приложения продолжала
работать с новой схемой: добавить колонку можно, переименовать нельзя.

**Копия базы снимается до миграций** — это единственная точка, откуда можно
вернуться, если неудачной окажется сама миграция.

### Настройка — один раз

Выполняется на сервере под `root`. Ключ выката создаётся здесь же и в
переписку не попадает: вы копируете его из своего терминала прямо в поле
настроек GitHub.

**1. Пользователь, от имени которого идёт выкат.** Отдельный, а не `root`:
ключ, лежащий в чужом сервисе, не должен открывать весь сервер.

```bash
adduser --disabled-password --gecos '' deploy
mkdir -p /home/deploy/.ssh && chmod 700 /home/deploy/.ssh
echo 'deploy ALL=(root) NOPASSWD: /opt/prodisser/deploy/update.sh' > /etc/sudoers.d/deploy
chmod 440 /etc/sudoers.d/deploy
visudo -c
```

**2. Ключ.** Создаётся на сервере, публичная половина сразу кладётся рядом:

```bash
ssh-keygen -t ed25519 -f /root/deploy_key -N '' -C 'github-deploy'
printf 'command="sudo -n /opt/prodisser/deploy/update.sh",restrict %s\n' \
  "$(cat /root/deploy_key.pub)" > /home/deploy/.ssh/authorized_keys
chown -R deploy:deploy /home/deploy/.ssh && chmod 600 /home/deploy/.ssh/authorized_keys
```

Приставка `command=` привязывает ключ к одной команде: даже попав в чужие
руки, он не даёт ни оболочки, ни файлов — только запуск обновления.

**3. Четыре значения для GitHub.** Печатаются на экран, копируются в
репозиторий: Settings → Secrets and variables → Actions → New repository
secret.

```bash
echo "DEPLOY_HOST = $(curl -s --max-time 5 ifconfig.me || echo 85.193.84.95)"
echo "DEPLOY_USER = deploy"
echo "DEPLOY_KNOWN_HOSTS = 85.193.84.95 $(cut -d' ' -f1,2 /etc/ssh/ssh_host_ed25519_key.pub)"
echo '--- DEPLOY_KEY: всё от BEGIN до END включительно ---'
cat /root/deploy_key
```

**Ключ вставляется целиком**: строка `-----BEGIN OPENSSH PRIVATE KEY-----`,
все строки тела и строка `-----END OPENSSH PRIVATE KEY-----`. Потерянная
строка или склеенные переносы дают при выкате `error in libcrypto`, а следом
общее «Permission denied», в котором настоящей причины не видно; поэтому
задача разбирает ключ до подключения и называет причину прямо.

**Закрытая половина ключа не пересылается никому и никуда**, кроме поля формы
в настройках репозитория: ни в переписку с исполнителем, ни в мессенджер, ни
в почту. Ключ, показанный где-то ещё, считается скомпрометированным — его
заменяют, повторив шаги 2 и 3 с новым файлом. Это то же правило, что для
паролей (Р-117), и оно не зависит от того, кому именно ключ показали.

После того как все четыре секрета сохранены, закрытая половина ключа на
сервере больше не нужна:

```bash
shred -u /root/deploy_key /root/deploy_key.pub
```

**Отпечаток сервера берётся из секрета, а не принимается на веру** при первом
подключении: иначе подмена узла прошла бы незамеченной, а на другом конце —
ключ, запускающий обновление.

### Как пользоваться

Ничего не нужно делать: слияние в `main` запускает выкат. Ход и журнал —
вкладка Actions, задача «Выкат на боевой сервер». Там же кнопка `Run
workflow` — ручной запуск, если надо поднять сервер после сбоя площадки без
новых правок.

Выкат не начнётся, пока проверка не стала зелёной, и два выката не пойдут
разом: очередь держится и на стороне GitHub, и блокировкой на сервере.

## 6. Аналитика

Яндекс.Метрика. Google Analytics не подходит по тем же причинам, что и
зарубежный хостинг.

Всё, что можно сделать без номера счётчика, сделано. Включение сводится к
одной переменной `NEXT_PUBLIC_METRIKA_ID` — она передаётся при сборке образа
(`docker compose build --build-arg NEXT_PUBLIC_METRIKA_ID=00000000`), потому
что переменные `NEXT_PUBLIC_*` вшиваются в разметку, а не читаются при
запуске.

Одна переменная переключает сразу четыре вещи, и в этом смысл: забыть
что-то одно невозможно.

| Что | Без номера | С номером |
|---|---|---|
| Счётчик на странице | не выводится | выводится после согласия посетителя |
| Уведомление о cookies | не показывается | показывается до первого выбора |
| Политика содержимого | закрыта полностью | разрешён `mc.yandex.ru` для сценария, пикселя, запросов и кадра |
| Раздел политики «Файлы cookies и веб-аналитика» | редакция «cookies не используются» | редакция со сведениями о счётчике |
| Дата редакции политики | 21 августа 2026, версия 1.0 | 13 сентября 2026, версия 1.1 |

**Согласие посетителя.** Счётчик запускается только после нажатия
«Разрешить» в уведомлении внизу страницы. До выбора со страниц не уходит ни
одного запроса к `mc.yandex.ru`; отказ запоминается так же, как согласие.
Выбор хранится в браузере посетителя под ключом `pd-analytics` и никуда не
передаётся. Это не украшение: правовым основанием обработки в политике
названо именно согласие, выражаемое в этом уведомлении.

**Вебвизор выключен намеренно** — он пишет содержимое полей формы, то есть
имя, телефон и тему работы, и передаёт их третьему лицу.

Осталось два действия заказчика.

1. **Завести счётчик** на своей учётной записи Яндекса и передать номер.
   Счётчик, заведённый исполнителем, останется у исполнителя вместе со
   статистикой.
2. **Обновить уведомление Роскомнадзора.** Уведомление подано 12.09.2026 без
   счётчика. Появляются: новое действие с данными (передача), новый
   получатель (ООО «ЯНДЕКС»), новая категория данных (сведения о посещении
   Сайта). Сведения в уведомлении обновляются до включения, а не после.

Новая редакция раздела политики уже написана и лежит в макете; юрист
проверяет её текст, а не пишет с нуля.

### 6.1. Как завести счётчик (действия заказчика)

Пятнадцать минут, ничего программировать не нужно. Код счётчика на сайт
вставлять НЕ надо — он уже в сборке и ждёт номер.

1. Войти на `metrika.yandex.ru` под **рабочей** учётной записью компании. Не
   под личной почтой сотрудника: счётчик остаётся у владельца учётной записи
   вместе со всей статистикой, и при смене сотрудника доступ теряется.
2. «Добавить счётчик». Имя — `ProDisser`. Адрес сайта — `prodisser.ru`; пока
   домена нет, можно указать любой рабочий и поправить позже, на сбор данных
   это не влияет.
3. Часовой пояс — Москва, валюта — рубль.
4. **Выключить «Вебвизор, карта скроллинга, аналитика форм».** По умолчанию
   переключатель включён. Вебвизор записывает, что человек печатает в полях
   формы, то есть имя, телефон и тему работы, и отправляет это Яндексу.
   Такая передача требует отдельного основания в политике и отдельной строки
   в уведомлении Роскомнадзора; сайт её не использует и код счётчика в
   сборке её не включает — но выключить надо и в настройках, чтобы никто не
   включил случайно.
5. Принять условия использования сервиса.
6. Скопировать **номер счётчика** — восемь цифр в списке счётчиков рядом с
   названием. Это всё, что нужно передать исполнителю.
7. По желанию: в настройках счётчика, вкладка «Доступ», выдать исполнителю
   доступ «на чтение» — тогда он проверит после включения, что данные идут.

После получения номера исполнитель пересобирает образ с
`NEXT_PUBLIC_METRIKA_ID` и выкладывает. Ничего другого делать не нужно.

### 6.2. Как обновить уведомление Роскомнадзора (действия заказчика)

Уведомление подано 12.09.2026, когда счётчика не было. Появление счётчика
меняет сведения в реестре, а об изменениях оператор обязан сообщить —
ч. 7 ст. 22 152-ФЗ. Подаётся не новое уведомление, а **информационное письмо
о внесении изменений** в уже поданные сведения.

Куда: портал персональных данных Роскомнадзора `pd.rkn.gov.ru`, раздел форм
электронных документов, либо через Госуслуги. Открывается ранее поданное
уведомление, правятся нужные поля, письмо подписывается и отправляется.
Срок отправки уточняет форма при подаче; тянуть не нужно — сведения
обновляются **до** включения счётчика, а не после.

Что именно меняется — четыре пункта, остальное не трогать:

| Поле уведомления | Что дописать |
|---|---|
| Перечень действий с персональными данными | добавить передачу (предоставление, доступ) |
| Лица, обрабатывающие данные по поручению оператора | ООО «ЯНДЕКС» — наименование, ИНН и адрес сверить по договору-оферте сервиса; основание — оферта на использование Яндекс.Метрики |
| Категории обрабатываемых данных | сведения о посещении Сайта: адрес соединения, сведения о браузере и устройстве, источник перехода, просмотренные страницы, дата и время посещения |
| Правовое основание | согласие субъекта, выражаемое в уведомлении о файлах cookies на Сайте |

Чего в уведомлении быть НЕ должно: трансграничной передачи (серверы сервиса
в России) и записи содержимого форм (вебвизор выключен). Если эти пункты
где-то проставлены — их снять, иначе сведения разойдутся с тем, что делает
сайт, а это первое, что сверяют при проверке.

Формулировки для всех четырёх полей уже есть в политике, раздел «Файлы
cookies и веб-аналитика» в редакции 1.1: их можно переносить в уведомление
как есть — тексты писались согласованными.
