### 1.3. ОЭ-3 по частям

1. **Как клиент видит куратора с ролью «Методолог» или «Научный редактор».**
   Варианты:
   - (а) «Куратор» для всех ролей, как в строке Э-10;
   - (б) «Куратор по специальности», «Методолог», «Научный редактор» — как
     состав команды на `/students`;
   - (в) «Куратор — методолог».

   Рекомендация: (а), если роль работы клиенту не нужна; иначе (в).
   Вариант (б) нарушает критерий Э-01: «куратор» должен быть названием
   роли `EXPERT`, а не одной из трёх ролей работы.
2. **Что клиент видит о менеджере.** Рекомендация: «Менеджер — {ФИО}» без
   регалий. Степень и специальность по В-12 принадлежат куратору.
3. **Форма регалий менеджера Т-11 (Р-297).** Рекомендация: убрать её у
   `MANAGER` и `HEAD`. Э-11 переносит правку на профиль куратора, поля
   `ExpertProfile` остаются.

## 4. Ветки переписки — одна модель без дублирования кода

**После ОЭ-1 и С-2 (03.10.2026).** Ветки `CLIENT_CURATOR` нет; куратор не участвует в `WORK_INTERNAL` и `HEAD_STAFF`. Модель — три ветки:
- `CLIENT_MANAGER` — клиент, менеджер, руководитель;
- `WORK_INTERNAL` — менеджер и руководитель;
- `HEAD_STAFF` — руководитель и менеджер.

Поля модерации и `stageId` у `Message` не нужны. `MessageThreadRead` остаётся: он нужен счётчикам руководителя (ОР-3). Общая основа строится в РК-07. Текст раздела ниже описывает полный вариант и выполняется в этом сокращённом составе.

Требования куратора дают три ветки: клиент — менеджер, клиент — куратор с
модерацией, внутренняя по работе. Требования руководителя добавляют
четвёртую — «руководитель ↔ сотрудник» (РК-07). Раздел E делает
руководителя участником внутренней ветки. Ниже — общая модель для всех
четырёх веток. План руководителя ссылается на этот раздел и не повторяет
его.

### 4.1. Данные — одна таблица `Message` и отметка прочтения участника

```prisma
enum MessageChannel {
  CLIENT_MANAGER  // прежняя переписка; значение для существующих строк
  CLIENT_CURATOR  // клиент — куратор, через модерацию (В-13)
  WORK_INTERNAL   // по работе: куратор, менеджер, руководитель; клиент не видит (В-14, РК-07)
  HEAD_STAFF      // руководитель — сотрудник, без работы (РК-07)
}

model Message {
  // прежние поля …
  projectId        String?          // пусто только у HEAD_STAFF
  channel          MessageChannel   @default(CLIENT_MANAGER)
  /// Сотрудник ветки «руководитель ↔ сотрудник»; у остальных веток пусто.
  staffId          String?
  /// Сообщение куратора клиенту и сообщение клиента куратору с контактом
  /// ждут решения. Прежние строки и остальные ветки опубликованы сразу.
  moderationStatus ModerationStatus @default(PUBLISHED)
  moderatedById    String?
  moderatedAt      DateTime?
  moderationNote   String?          @db.Text
  /// Этап, к которому задан вопрос (кнопка «Вопрос менеджеру»).
  stageId          String?

  @@index([projectId, channel, createdAt])
  @@index([staffId, createdAt])
}

/// Докуда участник прочитал ветку. Ключ ветки — «<канал>:<работа>» или
/// «HEAD_STAFF:<сотрудник>».
model MessageThreadRead {
  userId    String
  threadKey String
  readAt    DateTime
  @@id([userId, threadKey])
}
```

Ограничение в SQL миграции: у `HEAD_STAFF` задан `staffId` и пуст
`projectId`, у остальных веток — наоборот. Перечень `ModerationStatus`
общий с замечаниями и версиями (Р-226, Р-294).

**Почему одна таблица.** Четыре таблицы повторили бы:
- выборку и запись;
- счётчики и прочтение;
- обезличивание (`erasure.ts`);
- реестр «Контакты в переписке»;
- уведомления.

Один столбец ветки держит всё это в одном месте.

**Участники веток:**

| Ветка | Участники | Модератор | Кто ставит `Message.readAt` |
|---|---|---|---|
| `CLIENT_MANAGER` | клиент; менеджер работы; руководитель | — | у сообщения клиента — менеджер работы (Р-221); у сообщения практики — клиент |
| `CLIENT_CURATOR` | клиент; куратор работы | менеджер работы; руководитель — в любой работе | адресат: куратор или клиент |
| `WORK_INTERNAL` | куратор работы, менеджер работы, руководитель | — | первый прочитавший адресат |
| `HEAD_STAFF` | руководитель; сотрудник (`staffId`) | — | другая сторона |

**Прочтение — два разных вопроса, два поля без повторов.**

- **«Прочитал ли ответственный»** — `Message.readAt`, как сейчас. Его
  видит автор как отметку прочтения. По нему руководитель получает
  контрольное дело: сообщение клиента не прочитано менеджером дольше срока
  реакции (РК-05). Р-221 сохраняется: прочтение руководителем чужой работы
  `readAt` не ставит.
- **«Что непрочитано у меня»** — `MessageThreadRead`: курсор участника по
  ветке. Во внутренней ветке участников трое, и одного `readAt` для
  счётчиков не хватает. Курсор руководителя гасит его собственные
  счётчики. Поэтому «непрочитанные чужих работ» больше не висят у него
  делом «Ответить клиенту» (РК-05, наблюдение 7 части D).

Счётчики `unreadCount`, `unreadByProject` и `unreadInbox` переходят на
курсор. Прежний счёт по `readAt` остаётся только для отметки прочтения
автору и для контрольных дел.

### 4.2. Права — одна таблица в `lib/cabinet/access.ts`

```ts
type ThreadRef =
  | { channel: 'CLIENT_MANAGER' | 'CLIENT_CURATOR' | 'WORK_INTERNAL'; project: ProjectRef }
  | { channel: 'HEAD_STAFF'; staffId: string };
type ThreadRight = { read: boolean; write: boolean; moderate: boolean };
export function threadRights(actor: Actor, thread: ThreadRef): ThreadRight;
export function scopeMessages(actor: Actor, thread: ThreadRef): Prisma.MessageWhereInput;
```

- `MESSAGE_READ` и `MESSAGE_WRITE` остаются для `CLIENT_MANAGER`, чтобы не
  трогать существующие вызовы. Остальные ветки проверяются через
  `threadRights`.
- Куратор — только назначенный и с договором поручения
  (`isAssignedExpert`).
- `HEAD_STAFF`: читает и пишет руководитель и сам сотрудник; клиенту
  ветка недоступна.
- `scopeMessages` повторяет приём `scopeComments`:
  - не модератор видит опубликованные сообщения и свои;
  - клиенту ветки `WORK_INTERNAL` и `HEAD_STAFF` не отдаются условием
    выборки, даже если право проверено ошибочно.

### 4.3. Службы — один модуль `lib/cabinet/messages.ts`

## 5. Пометка «сдан куратором» без нового состояния

**Почему не новое значение `StageState`.** `StageState` читают:
- подписи клиента;
- срок согласования (Р-290);
- «Сегодня» и светофор;
- аналитика;
- напоминания о сроке;
- `turnLabel`.

Новое значение затронуло бы их все и изменило бы экран клиента. Э-05 же
требует: «состояние этапа для клиента не меняется».

**Поля (миграция `stage_handover`).**

```prisma
model Stage {
  // …
  /// Куратор сдал этап менеджеру (требование Э-05). Гаснет при отзыве,
  /// при возврате менеджером и при уходе этапа из «В работе».
  handedOverAt   DateTime?
  /// «Что сделано и на что обратить внимание клиента» — черновик «Итога
  /// этапа» у менеджера. Обезличивание затирает поле.
  handoverNote   String?   @db.Text
  /// Последний возврат куратору менеджером (М-25) и его причина.
  handbackAt     DateTime?
  handbackReason String?   @db.Text
}
```

**Производное состояние** — чистая функция в `lib/cabinet/stage-state.ts`:

```ts
export type Handover = 'none' | 'handed' | 'handed-back';
export function handoverOf(stage: {
  state: StageStateKey; handedOverAt: Date | null; handbackAt: Date | null;
}): Handover {
  if (stage.state !== 'IN_PROGRESS') return 'none';
  if (stage.handedOverAt !== null) return 'handed';
  return stage.handbackAt !== null ? 'handed-back' : 'none';
}
```

**Переходы** — в `lib/cabinet/handover.ts`, права — в `access.ts`:

| Действие | Кто | Условие | Запись |
|---|---|---|---|
| Сдать этап | назначенный куратор с договором | работа открыта; этап «В работе», не сдан; есть версия куратора в этапе, не отклонённая (Д-3); записка 1…10 000 знаков | `updateMany where {id, state: IN_PROGRESS, handedOverAt: null}` → `handedOverAt`, `handoverNote`; outbox менеджеру; журнал; событие истории для практики |
| Отозвать | тот же куратор | `handover = 'handed'` | `updateMany where handedOverAt not null` → `handedOverAt = null` |
| Вернуть куратору | менеджер работы, руководитель | `handover = 'handed'`; причина обязательна | `handedOverAt = null`, `handbackAt`, `handbackReason`; outbox куратору |
| Решение менеджера по состоянию | менеджер работы, руководитель | уход из «В работе» | `setStageState` гасит все четыре поля |
| Замена куратора | менеджер работы, руководитель | смена `expertId` | гасит `handedOverAt` (Д-6) |

«Пока менеджер не принял решение» означает: этап «В работе» и
`handedOverAt` задан. Возврат менеджером и любой перевод состояния гасят
пометку, после этого отзыв невозможен.

**Чтение.**
- `turnLabel`: «Этап сдан {дата}: ход за менеджером».
- Дела куратора (Э-04): сданный этап — не дело.
- Дело менеджера «Куратор сдал этап».
- Напоминание о сроке куратору: при `handed` не уходит (Р-301
  дополняется).
- Форма «На согласование»: `outcome ?? handoverNote`.
- Клиенту поля не отдаются — проверяется тестом на данные.
