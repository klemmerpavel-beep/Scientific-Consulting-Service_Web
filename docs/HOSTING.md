# Как купить хостинг и опубликовать сайт

Инструкция для владельца, от пустого места до работающего
`https://prodisser.ru`. Все действия выполняете вы: ни пароля, ни ключа,
ни доступа к серверу никому передавать не нужно.

Домен `prodisser.ru` уже зарегистрирован в Рег.ру, DNS-серверы —
`ns1.hosting.reg.ru` и `ns2.hosting.reg.ru`. Домен никуда не переносится:
он остаётся там, где есть, и начинает указывать на новый сервер.

**Порядок жёсткий, менять его нельзя.** Сертификат не выдадут, пока
не разошёлся DNS; сайт нельзя собрать, не зная его адреса; nginx
не запустится, если положить рабочую настройку до выпуска сертификата.
Каждый шаг заканчивается проверкой — не переходите к следующему, пока
проверка не прошла.

Время: около часа работы и от часа до суток ожидания DNS между шагами 6 и 7.

| Шаг | Что делаете | Где |
|---|---|---|
| 1 | Выбираете площадку, проверяете реестр РКН | браузер |
| 2 | Создаёте сервер | панель Timeweb |
| 3 | Первый вход, подкачка, межсетевой экран, Docker | терминал |
| 4 | Кладёте проект на сервер | терминал |
| 5 | Заполняете `deploy/.env` | терминал |
| 6 | Направляете домен на сервер | панель Рег.ру |
| 7 | Заводите почту на домене | панель Рег.ру |
| 8 | Запускаете сайт и выпускаете сертификат | терминал |
| 9 | Ставите расписания | терминал |
| 10 | Проверяете, что всё работает | браузер и терминал |
| 11 | Правовые действия после покупки | браузер |

## Что именно покупается

| Что | Где | Сколько в месяц |
|---|---|---|
| Облачный сервер (VPS) — на нём и сайт, и база | Timeweb Cloud | ~880–950 ₽ |
| Внешний адрес IPv4 к серверу | там же | ~190 ₽ |
| Почта `info@prodisser.ru` | Рег.ру, тариф Mail‑1 | 0 ₽ |
| Домен `prodisser.ru` | Рег.ру | уже оплачен |

**Отдельную «базу данных» покупать не надо.** PostgreSQL поднимается на том
же сервере вместе с сайтом — так уже настроено в `deploy/docker-compose.yml`.
Управляемая база у провайдера стоит ещё 700–900 ₽ в месяц и на этом объёме
не даёт ничего: заявок единицы в день, а держать данные в одном месте проще
и для резервного копирования, и для объяснения проверяющему. Выносить базу
отдельно будет смысл, когда появятся кабинет и админ-панель.

Итого около 1100 ₽ в месяц — чуть выше вашего ориентира в 1000 ₽.
Конфигурация с 1 ГБ памяти дешевле, но на ней не соберётся образ
приложения: сборке нужен пик около гигабайта.

## Шаг 1. Выбрать площадку

**Рекомендация: Timeweb Cloud, конфигурация «Cloud MSK 40» —
2 vCPU / 2 ГБ / 40 ГБ NVMe, регион Москва.**

Почему он:

- В реестре хостинг-провайдеров Роскомнадзора. Это не пожелание, а условие:
  размещаться у провайдера вне реестра с декабря 2023 года нельзя.
- Почасовая тарификация. Можно поднять сервер, проверить и погасить,
  заплатив за несколько часов.
- Серверы в Москве и Петербурге. Требование ч. 5 ст. 18 152-ФЗ: база
  с данными граждан России физически в России.

Равноценные варианты:

| Провайдер | Цена 2 ГБ | Замечание |
|---|---|---|
| **Selectel** | ~940 ₽ | инфраструктура крупнее, панель сложнее |
| **Beget** | дешевле | проще, меньше настроек |
| **Рег.ру** (VDS SSD‑2) | ~1190 ₽ | всё в одном кабинете с доменом, но дороже |

Вариант «всё у Рег.ру» удобен одним счётом и одной панелью. Он дороже
примерно на 300 ₽ в месяц; техническая разница для нашей задачи нулевая,
инструкция ниже подходит и ему — меняется только вид панели на шаге 2.

**Цены перепроверьте на день покупки.** С 1 января 2026 года Рег.ру поднял
цены, Timeweb и Selectel поднимали на рубеже 2025–2026 на 8–20 %.

**Чего не делать.** Не брать зарубежный VPS, Vercel, Netlify, Hetzner,
DigitalOcean — никакие. И **не ставить Cloudflare** перед сайтом: он
пропускает трафик и расшифровывает его на своих серверах за границей,
а это ровно та трансграничная передача, которой раздел 9 нашей политики
не допускает. Ловушка в том, что бесплатный Cloudflare выглядит
безобидным «ускорением», и о нём легко забыть, заполняя уведомление
Роскомнадзора.

### Что сделать до оплаты — это важнее выбора тарифа

1. Откройте [реестр хостинг-провайдеров РКН](https://rkn.gov.ru/activity/connection/register/p1578/),
   найдите провайдера (Timeweb — АО «ТаймВеб»), **сохраните снимок экрана
   с датой**. Это ваше доказательство добросовестности, если спросят,
   почему выбран именно он.
2. Оформляйте договор **на ООО «РУСДРОН»**, а не на физическое лицо.
   Политика (раздел 8) говорит, что обработка поручается третьим лицам
   на основании договора с обязанностью соблюдать конфиденциальность;
   договор с частным лицом этому не соответствует, и закрывающих
   документов для бухгалтерии не будет.
3. Скачайте договор-оферту провайдера, найдите в нём раздел про
   персональные данные и конфиденциальность, сохраните файл.
4. **Выпишите наименование и юридический адрес провайдера** — их нужно
   внести в раздел 8 политики (шаг 11).

## Шаг 2. Создать сервер

Панель Timeweb Cloud → «Облачные серверы» → «Создать».

| Параметр | Значение |
|---|---|
| Регион | Москва |
| Образ | Ubuntu 24.04 LTS |
| Конфигурация | 2 vCPU / 2 ГБ / 40 ГБ NVMe |
| Публичный IPv4 | включить (платный, ~190 ₽/мес) |
| Доступ | **SSH-ключ**, не пароль |

Если ключа нет, сделайте его **на своём компьютере**, не на сервере:

```bash
ssh-keygen -t ed25519 -C "prodisser"
cat ~/.ssh/id_ed25519.pub
```

Вывод второй команды — одна строка, начинается с `ssh-ed25519` — вставляется
в панель. Файл `id_ed25519` без `.pub` секретный: его никуда не отправляют,
не показывают и не копируют на сервер. Вход по паролю подбирают роботы
в первые же часы жизни сервера; вход по ключу — нет.

После создания панель покажет адрес вида `92.51.xx.xx`. **Запишите его** —
он понадобится на шаге 6. Дальше в инструкции он обозначен как `ВАШ_IP`.

**Проверка шага:** `ssh root@ВАШ_IP` пускает на сервер без запроса пароля.

## Шаг 3. Подготовить сервер

Всё дальнейшее — на сервере, после `ssh root@ВАШ_IP`.

```bash
apt update && apt upgrade -y
```

**Файл подкачки.** Без него сборка образа падает: памяти два гигабайта,
а сборке нужен пик около гигабайта сверх работающей системы.

```bash
fallocate -l 2G /swapfile && chmod 600 /swapfile
mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
free -h            # в строке Swap должно появиться 2,0Gi
```

**Межсетевой экран.** Открыты ровно три порта:

```bash
ufw allow OpenSSH
ufw allow 80/tcp
ufw allow 443/tcp
ufw --force enable
ufw status
```

Порт базы `5432` наружу **не открывается никогда**: приложение и база
общаются внутри Docker, снаружи база доступна быть не должна.

**Docker:**

```bash
curl -fsSL https://get.docker.com | sh
docker --version && docker compose version
```

**Проверка шага:** `free -h` показывает 2 ГБ подкачки, `ufw status`
показывает три правила, `docker compose version` печатает версию.

## Шаг 4. Положить проект на сервер

Код лежит в GitHub, сервер забирает его оттуда. «Запушить сайт» —
это `git pull` на сервере и пересборка, отдельной выкладки файлов нет.

```bash
apt install -y git
mkdir -p /opt && cd /opt
git clone https://github.com/klemmerpavel-beep/Scientific-Consulting-Service_Web.git prodisser
cd /opt/prodisser
git log --oneline -1
```

Если репозиторий закрытый, GitHub попросит имя и токен. Токен создаётся
в GitHub: Settings → Developer settings → Personal access tokens →
Fine-grained tokens, доступ только на чтение только этого репозитория.
**Токен — это пароль:** не вставляйте его в переписку и не храните
в открытых файлах.

**Проверка шага:** `ls /opt/prodisser/deploy` показывает `docker-compose.yml`,
`nginx.conf`, `nginx-bootstrap.conf`, `backup.sh`, `retention.sh`.

## Шаг 5. Заполнить настройки

```bash
cd /opt/prodisser
cp deploy/.env.deploy.example deploy/.env
chmod 600 deploy/.env
nano deploy/.env
```

Что вписать:

```
NEXT_PUBLIC_SITE_URL=https://prodisser.ru

POSTGRES_DB=prodisser
POSTGRES_USER=prodisser
POSTGRES_PASSWORD=длинный_случайный_пароль

# заполняется на шаге 7
SMTP_HOST=
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=
SMTP_PASSWORD=
SMTP_FROM=ProDisser <site@prodisser.ru>
LEAD_MAIL_TO=info@prodisser.ru

# необязательно, см. ниже
TELEGRAM_BOT_TOKEN=
TELEGRAM_CHAT_ID=
```

Пароль базы сгенерируйте, а не придумывайте:

```bash
openssl rand -base64 24
```

`NEXT_PUBLIC_SITE_URL` обязателен **на сборке**, а не только при запуске:
из него вычисляются `canonical`, Open Graph, `robots.txt` и карта сайта.
Соберёте без него — карта сайта уйдёт с относительными адресами
и станет недействительной для поисковиков.

**Telegram — канал необязательный.** В мессенджер приходит только сигнал:
страница, форма, время и номер заявки, без имени, контакта и темы работы.
Так сделано намеренно: Telegram работает на серверах за пределами России,
и отправка туда содержания заявки была бы трансграничной передачей,
которой наша политика не допускает. Токен берётся у `@BotFather`,
идентификатор чата — у `@getidsbot`. Оставите поля пустыми — приём заявок
работает как обычно: заявка сохраняется в базе и приходит на почту.

**Проверка шага:** `grep -c '=' deploy/.env` печатает число, а
`cat deploy/.env` не содержит незаполненного `POSTGRES_PASSWORD=`.

## Шаг 6. Направить домен на сервер

Кабинет Рег.ру → «Домены» → `prodisser.ru` → вкладка «Управление» →
«DNS-серверы и зона» → «Изменить».

DNS-серверы `ns1.hosting.reg.ru` и `ns2.hosting.reg.ru` **оставляем как есть**:
зона правится прямо здесь, менять их не нужно.

Нужны две записи типа **A**:

| Тип | Имя | Значение |
|---|---|---|
| A | `prodisser.ru` (или `@`) | `ВАШ_IP` |
| A | `www.prodisser.ru` (или `www`) | `ВАШ_IP` |

**Если такие записи уже есть** и ведут на парковку Рег.ру — исправьте их,
**не добавляйте вторые**. Две записи A на одно имя означают, что половина
посетителей попадёт на старый адрес, и выглядит это как «сайт открывается
через раз».

Дальше нужно подождать. Изменения расходятся от часа до суток.

**Проверка шага** — с любого компьютера, не с сервера:

```bash
dig +short prodisser.ru
dig +short www.prodisser.ru
```

Обе команды должны напечатать `ВАШ_IP`. Пока печатают старое или ничего —
**к шагу 8 не переходите**, сертификат не выдастся.

## Шаг 7. Почта на домене

Ящик `info@prodisser.ru` **обязателен**: этот адрес уже напечатан в оферте,
политике и согласии как единственный контакт оператора. Открыть сайт
с адресом, который не принимает писем, значит не исполнить собственный
документ с первого дня.

Кабинет Рег.ру → «Почта» → «Почта на домене» → `prodisser.ru` →
тариф **Mail‑1** (бесплатный, до 1000 ящиков, 10 ГБ).

Заведите два ящика:

- `info@prodisser.ru` — тот, что в документах, для людей;
- `site@prodisser.ru` — от него сайт отправляет письма о заявках.

Рег.ру сам добавит в зону записи **MX**, **SPF** (`TXT` со значением
`v=spf1 …`) и **DKIM**. Проверьте, что они появились, и **не удаляйте**
их, правя записи A из шага 6: это разные записи, они спокойно уживаются
в одной зоне. Без SPF и DKIM письма о заявках будут падать в спам.

Впишите реквизиты в `deploy/.env` (хост уточните в панели Рег.ру,
он может отличаться):

```
SMTP_HOST=mail.hosting.reg.ru
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=site@prodisser.ru
SMTP_PASSWORD=пароль_ящика
SMTP_FROM=ProDisser <site@prodisser.ru>
LEAD_MAIL_TO=info@prodisser.ru
```

**Проверка шага** — прямо с сервера, до публикации сайта:

```bash
printf 'From: site@prodisser.ru\nTo: info@prodisser.ru\nSubject: Proverka\n\nProverka\n' > /tmp/m.txt
curl --url "smtps://mail.hosting.reg.ru:465" --ssl-reqd \
  --mail-from "site@prodisser.ru" --mail-rcpt "info@prodisser.ru" \
  --upload-file /tmp/m.txt --user "site@prodisser.ru:ПАРОЛЬ_ЯЩИКА"
rm /tmp/m.txt
```

Команда молчит, если письмо ушло, и печатает ошибку, если нет. Письмо
должно прийти на `info@prodisser.ru` — проверьте и папку «Спам».

## Шаг 8. Запустить сайт и выпустить сертификат

Здесь важен порядок. В `deploy/nginx.conf` прописаны пути к сертификату,
которого пока нет, и nginx с такой настройкой **не запустится**:

```
[emerg] cannot load certificate "/etc/letsencrypt/live/prodisser.ru/fullchain.pem"
```

А certbot, чтобы выдать сертификат, должен получить ответ по адресу
`http://prodisser.ru/.well-known/acme-challenge/…` — то есть nginx уже
должен работать. Круг разрывает временная настройка
`deploy/nginx-bootstrap.conf`: только порт 80, только каталог проверки,
ни одного упоминания SSL.

### 8.1. Поднять приложение и базу

```bash
cd /opt/prodisser

# сначала схема базы: без неё приложению некуда писать заявки
docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
  --profile migrate run --rm migrate

# потом сборка и запуск
docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
  up -d --build

curl -s http://127.0.0.1:3000/api/health
```

Ожидается `{"ok":true,"db":true}`. Первая сборка идёт 5–10 минут.

Приложение слушает только `127.0.0.1:3000` и снаружи недоступно —
так и должно быть.

### 8.2. Временный nginx и сертификат

```bash
apt install -y nginx certbot
mkdir -p /var/www/certbot

rm -f /etc/nginx/sites-enabled/default
cp deploy/nginx-bootstrap.conf /etc/nginx/sites-available/prodisser
ln -sf /etc/nginx/sites-available/prodisser /etc/nginx/sites-enabled/prodisser
nginx -t && systemctl restart nginx

certbot certonly --webroot -w /var/www/certbot \
  -d prodisser.ru -d www.prodisser.ru \
  --agree-tos -m info@prodisser.ru --no-eff-email
```

`--webroot`, а не `--nginx`: certbot не трогает нашу настройку, а значит
и продление через 90 дней пройдёт само, без вмешательства. Задание
на продление ставит сам пакет certbot.

Если certbot ругается, что не может достучаться до домена, — вернитесь
к проверке шага 6: DNS ещё не разошёлся.

### 8.3. Рабочий nginx

```bash
cp deploy/nginx.conf /etc/nginx/sites-available/prodisser
nginx -t && systemctl reload nginx
```

`nginx -t` обязателен перед `reload`: он ловит ошибку до того, как она
уронит работающий сайт.

**Проверка шага:**

```bash
curl -sI http://prodisser.ru | head -1          # 301
curl -sI https://www.prodisser.ru | head -1     # 301
curl -s https://prodisser.ru/api/health         # {"ok":true,"db":true}
```

## Шаг 9. Расписания

```bash
crontab -e
```

Добавить две строки:

```
0 3 * * * /opt/prodisser/deploy/backup.sh >> /var/log/prodisser-backup.log 2>&1
30 3 * * 1 /opt/prodisser/deploy/retention.sh >> /var/log/prodisser-retention.log 2>&1
```

Первая снимает ночную копию базы, хранит 30 дней, проверяет целостность
архива до замены вчерашней копии. Вторая **обязательна**: она удаляет
заявки старше года, по которым не заключён договор, — это исполнение
пункта 7.1 политики. Обещание в тексте без исполнения в коде проверяется
одним запросом к базе, и расхождение видно сразу.

Копии остаются на сервере в России. Выгружать их в зарубежное хранилище
нельзя: копия — это та же обработка персональных данных.

**Проверка шага** — запустить оба скрипта руками, не дожидаясь ночи:

```bash
/opt/prodisser/deploy/backup.sh
/opt/prodisser/deploy/retention.sh
ls -lh /opt/prodisser/deploy/backups/
```

## Шаг 10. Проверить, что всё работает

```bash
curl -s https://prodisser.ru/api/health          # {"ok":true,"db":true}
curl -sI https://prodisser.ru | grep -iE 'content-security|strict-transport|x-frame|x-content'
curl -s https://prodisser.ru/sitemap.xml | head  # настоящий домен, не localhost
curl -s https://prodisser.ru/robots.txt
```

Заголовков должно быть четыре: `Content-Security-Policy`,
`Strict-Transport-Security`, `X-Frame-Options`, `X-Content-Type-Options`.

Адрес заявителя нельзя подделать — проверяется так:

```bash
curl -s https://prodisser.ru/api/lead -H 'content-type: application/json' \
  -H 'X-Forwarded-For: 1.2.3.4' -H 'X-Real-IP: 5.6.7.8' \
  -d '{"source":"landing","form":"proverka","contactKind":"email","contact":"proverka@example.com","consent":true,"elapsed":9000}'
```

Заявка сохранится, но в журнале согласий должен оказаться ваш настоящий
адрес, а не `1.2.3.4` и не `5.6.7.8`:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec -T db \
  psql -U prodisser -d prodisser -c 'select form, ip from "Lead" where form = '"'"'proverka'"'"''
```

Потом уберите проверочную запись:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec -T db \
  psql -U prodisser -d prodisser -c 'delete from "Lead" where form = '"'"'proverka'"'"''
```

И вручную, с телефона:

- [ ] `https://prodisser.ru` открывается, замок в адресной строке целый
- [ ] `http://` и `www` перенаправляют на основной адрес
- [ ] заявка с формы уходит, показывается подтверждение
- [ ] письмо пришло на `info@prodisser.ru`
- [ ] в Telegram пришёл сигнал **без** имени, контакта и темы работы

## Шаг 11. Правовые действия после покупки

Без этого запуск неполный.

1. **Внести наименование и адрес провайдера в раздел 8 политики.**
   Состав сведений в согласии по закону включает наименование и адрес
   лица, обрабатывающего данные по поручению оператора. Сейчас там
   написано «предоставляются по запросу» — так можно до покупки, но
   не после. Пришлите мне реквизиты, правка занимает пять минут.
2. **Подать уведомление в Роскомнадзор** — до открытия сайта, не после.
   В графе о трансграничной передаче указывается «не осуществляется».
   Условие выполнено, пока хостинг и почта российские, а в Telegram
   уходит сигнал без персональных данных. Подключите зарубежный ящик,
   счётчик посещаемости или верните содержание заявки в мессенджер —
   графа станет ложной, и уведомление придётся подавать заново.
3. Сложить в одну папку: договор с провайдером, снимок реестра РКН
   с датой, подтверждение подачи уведомления. Это весь пакет, который
   спрашивают при проверке.

## Как выкладывать изменения дальше

Правки вносятся в репозиторий, сервер их забирает:

```bash
cd /opt/prodisser
git pull

# только если менялась схема базы
docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
  --profile migrate run --rm migrate

docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
  up -d --build

curl -s https://prodisser.ru/api/health
```

Сборка идёт в стороне, а старый контейнер работает до её конца — сайт
во время обновления не падает. Заявки, база и сертификат не трогаются.

**Если после обновления что-то сломалось**, откат — на предыдущий коммит:

```bash
cd /opt/prodisser
git log --oneline -5          # найти рабочий коммит
git checkout <хэш>
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --build
```

Откат схемы базы автоматом не делается. Если ломается после миграции —
восстанавливайте базу из ночной копии:

```bash
gzip -dc deploy/backups/prodisser_ГГГГ-ММ-ДД_ЧЧММ.sql.gz \
  | docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec -T db \
      sh -c 'psql -U "$POSTGRES_USER" -d postgres -c "create database restore_check" \
             && psql -U "$POSTGRES_USER" -d restore_check'
```

Копия сначала разворачивается в `restore_check` — на рабочую базу
её никогда не льют вслепую.

## Если что-то пошло не так

| Симптом | Причина, которая встречается чаще всего |
|---|---|
| `dig` показывает старый адрес | DNS ещё не разошёлся; ждать до суток |
| `nginx -t`: cannot load certificate | положили `nginx.conf` до выпуска сертификата — вернитесь к 8.2 |
| certbot: не может достучаться до домена | DNS не разошёлся, либо закрыт порт 80, либо не удалён `sites-enabled/default` |
| Сборка падает без внятной ошибки | нет файла подкачки, кончилась память (шаг 3) |
| `{"ok":true,"db":false}` | база не поднялась или неверный `POSTGRES_PASSWORD` |
| Сайт отдаёт 502 | контейнер приложения не запустился: `docker compose -f deploy/docker-compose.yml logs web` |
| Заявка не приходит на почту | неверный `SMTP_HOST`; проверить командой из шага 7 |
| Письма падают в спам | в зоне нет записей SPF и DKIM (шаг 7) |
| Сайт открывается через раз | две записи A на одно имя (шаг 6) |
| Место кончилось | `docker system prune -f` — Docker копит старые слои |

Посмотреть, что происходит:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml ps
docker compose --env-file deploy/.env -f deploy/docker-compose.yml logs --tail=50 web
docker compose --env-file deploy/.env -f deploy/docker-compose.yml logs --tail=50 db
journalctl -u nginx --no-pager -n 30
```

## Что здесь проверено, а что нет

Проверено на этой машине, а не написано по памяти: настройка nginx
из `deploy/nginx.conf` проходит `nginx -t` и в связке с приложением
отдаёт 301 с `http` и с `www`, 200 по основному адресу с HTTP/2 и всеми
четырьмя заголовками безопасности; `deploy/nginx-bootstrap.conf` отдаёт
каталог проверки certbot и 404 на остальное; подделка `X-Forwarded-For`
и `X-Real-IP` в запросе заявки не проходит — в журнал согласий пишется
настоящий адрес соединения; запрос удаления по сроку хранения удаляет
запись возрастом 13 месяцев и не трогает свежую.

Не проверено, потому что требует настоящего домена и оплаченного
сервера: выпуск сертификата certbot, доставка почты через Рег.ру,
расхождение записей DNS. Эти шаги описаны по документации провайдеров
и проверяются вами на месте — у каждого есть своя проверка в конце шага.
