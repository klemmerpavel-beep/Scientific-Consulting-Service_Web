## 4. Правила реализации

1. **Репозиторий и ветка.** Работа идёт в этом репозитории, на ветке
   `claude/brave-pasteur-yehkoc` от `24f36f2`. Запрос на слияние в `main` —
   по указанию владельца.
2. **Одно требование — один коммит** с номером Т в заголовке («Т-03: …»).
   Единственное отступление — Т-01 в два коммита (раздел 10, п. 1).
3. **Записи в документах.** Каждый коммит, которому нужно новое Р
   (раздел 2.5), добавляет запись в `docs/DECISIONS.md` (с разбором) и
   строку в `docs/DECISIONS-SUMMARY.md`. После каждого Т обновляется
   `client-cabinet-guide.md`: в первом коммите реализации он вместе с
   файлом требований переносится в `docs/` этого репозитория. Сейчас он
   лежит в другом репозитории (`Scientific-Consulting-Service`, ветка
   `claude/prodisser-cabinet-audit-5pe89v`).
4. **Права** проверяются только на сервере, через `lib/cabinet/access.ts`:
   - разрешения — через `can`/`ensure`;
   - выборки — через `scope*`;
   - поля — через `present*`.

   Скрытие формы на экране само по себе правом не считается.
5. **Тексты** для клиента — по словарю части C. Термины оферты в
   юридическом смысле сохраняются.
6. **Без новых зависимостей** (CONTRIBUTING п. 5): производственный
   календарь, проверка сигнатур файлов и заготовки делаются без библиотек.
7. **Визуальный стиль и состав меню не меняются.** Меняется только подпись
   пункта по Т-08. Действуют пределы:
   - пять функциональных блоков на экране (Р-183);
   - один акцент на экран;
   - зелёный и красный — только исход действия (Р-146).
8. **Страницы сайта** правятся в `design/*.dc.html` с переносом
   конвертером (CONTRIBUTING). Код кабинета пишется вручную (Р-122).
9. **Проверки перед каждым коммитом.** Выполняются в этой среде: здесь
   есть PostgreSQL 16, Node 22 и Chromium.
   - `npm run typecheck`, `npm test`, `npm run test:db` на локальной
     PostgreSQL, `npm run build`, `npm run build:preview`;
   - при правке макетов — перенос и `git diff --exit-code`;
   - при правке кабинета — пересъёмка снимков: `tools/cabinet-artboards.mjs`,
     `tools/cabinet-prototype.mjs`, `tools/cabinet-portable.mjs`. Без неё
     падает проверка отпечатка (Р-214);
   - axe и переполнения на ширинах от 360 до 1440 px.
10. **Миграции**: одна на каждое Т, меняющее схему. В том же коммите
    обновляется `LATEST_MIGRATION` (`lib/schema-version.ts:13`, Р-218), а
    новые персональные поля включаются в обезличивание (Р-234,
    `lib/cabinet/erasure.ts`).

### Т-01 · Почта на домене, Telegram, очередь · блокирует открытие

**Сверка с кодом.**

Адрес `info.prodisser@gmail.com` встречается:

- в макетах `design/`:
  - `StartPage.dc.html:394`;
  - `MainPage:516, 683`, `StudentsPage:564, 741`, `BusinessPage:552, 727`;
  - `NotFoundPage:55`;
  - `ConsentPage:149, 158` (отзыв согласия);
  - `PrivacyPage:142, 150`;
  - `OfferPage:149, 155`;
- вне макетов: `components/OrgSchema.tsx:24`, `LICENSE:49, 90`, `SECURITY.md:9`.

Заглушка кабинета при этом уже называет другой адрес — `info@prodisser.ru`
(`app/cabinet/layout.tsx:61`).

Почта уходит двумя ветками на одних настройках `SMTP_*`:
`lib/notify.ts:196–230` и `lib/cabinet/mail.ts:90–115`. Найдены дефекты:

- **пустой отправитель.** `SMTP_FROM ?? SMTP_USER` не срабатывает на пустую
  строку, которую подставляет compose (`${SMTP_FROM:-}`), и поле From
  остаётся пустым (`mail.ts:100`, `notify.ts:219`);
- **нет Reply-To** — ответ клиента уйдёт на служебный ящик;
- **накопленная очередь.** Строки «канал не настроен» копятся без срока
  (`outbox.ts:344–354`). При включении почты уйдёт всё накопленное, включая
  напоминания о сроках, которые уже прошли;
- **документация.** DMARC не описан нигде. `RELEASE.md` (Reg.ru) и
  `DEPLOY.md` (Яндекс 360) расходятся в выборе почтовой площадки.

**Делается.** Т-01 выпускается двумя коммитами (раздел 10, п. 1).

Т-01а — код и документация:

- отправитель берётся через `||`, а не `??`; `mailConfigured()` требует
  непустого отправителя;
- Reply-To — контактный адрес ProDisser;
- одна константа контактов (`lib/practice-contacts.ts`) для писем, кабинета
  и `OrgSchema`. Значение — адрес из действующих правовых текстов (О-7);
- срок годности строк очереди:
  - напоминание о сроке после наступления срока не отправляется;
  - строка старше суток для событий, где это указано, переходит в
    состояние «просрочено» без отправки;
- в `DEPLOY.md` и `RELEASE.md` 4.1:
  - DMARC (`p=none`, затем `quarantine`);
  - выбор одной почтовой площадки;
  - порядок приёмки доставки на ящиках Яндекс, Mail.ru, Gmail и вузовском.

Т-01б — после одобрения юриста и запуска ящика (О-7):

- замена адреса в 8 макетах с переносом, в `OrgSchema.tsx`, `LICENSE` и
  `SECURITY.md`;
- новая дата редакции трёх правовых документов;
- значение константы контактов меняется на `info@prodisser.ru`.

**Вне кода — владелец:**

## 10. Решения по умолчанию, принимаемые вместе с планом

Это мелкие развилки, которые вопросом не выносились. Согласование плана
означает их принятие; каждую можно изменить ответом на план.

1. **Т-01 — два коммита.** Т-01а — код; Т-01б — смена адреса после юриста.
   Это отступление от правила «одно требование — один коммит»: вторая часть
   зависит от внешнего события.
2. **Т-03 — длина текста.** Текст замечаний обязателен (непустой после
   обрезки пробелов); минимальной длины нет.
3. **Т-04 — подпись поля.** «Ваши ФИО»; подсказка — «Если работа
   оформляется на другого человека, укажите его ФИО». Р-191 разрешает
   оформление на другое лицо, и подсказка этот случай сохраняет.
4. **Т-15 — переключатель и сроки:**
   - переключатель `APPROVAL_AUTO_ACCEPT` в `deploy/.env`, по умолчанию
     выключен;
   - при выключенном — дата и ссылка на п. 7.2 без фразы о последствии,
     кнопки доступны и после срока;
   - срок не меньше 5 рабочих дней;
   - календарь — таблица, его правит руководитель;
   - этапам, стоящим на согласовании при выкате, срок считается от дня
     выката.
5. **Т-16 — содержание письма.** Куратору уходит сигнал без текста
   замечаний — то же правило, что для переписки.
6. **Т-17 — для кого правило.** *Заменено требованием М-10 (раздел 12,
   п. 1): закрытая работа — только чтение для всех ролей.* На завершённом
   этапе действующей работы текст — «Этап завершён. Если нужно передать
   файл, напишите куратору»: формулировка «Работа закрыта» здесь была бы
   неверна.
7. **Т-18 — устройство модерации:**
   - отдельная таблица модерации;
   - право публикации — `COMMENT_MODERATE`;
   - номера версий не перенумеровываются;
   - пояснение эксперта публикуется вместе с версией.
8. **Т-19 — тексты:**
   - подпись строки — «Корректировка суммы»;
   - у действующей работы пояснение — «сумма к оплате изменена по
     договорённости»;
   - события о документах скрытых траншей клиенту не показываются.
9. **Т-20 — где заготовки.** Только на экране переписки, без кода в
   браузере; карточка работы не меняется.
10. **Т-22 — перечень.** Список расширений — в описании Т-22. Разрешены sh,
    py, R, m, ipynb, docm, xlsm и архивы.
11. **Т-24 — заявка из кабинета и тексты шагов.** Блок «Что будет дальше»
    показывается и после формы «Новая заявка» в кабинете; тексты трёх шагов

12. **Т-25 — нужен ответ владельца.** Кто такой «эксперт» в обещании

    - Если это куратор — заменить на «профиль куратора и список его
      публикаций».
    - Если исполнитель — снять упоминание публикаций.

    По умолчанию — первый вариант.
13. **Т-10 — кнопка и тексты.** Кнопка «Подключить Telegram» показывается,
    только если бот настроен и Telegram ещё не подключён; тексты трёх строк
    — в описании Т-10.
14. **Т-02 — кому ссылка.** Ссылка «Оплаты и документы» в шапке колонки — у
    клиента; кнопка сотрудников в «Управлении работой» остаётся.
